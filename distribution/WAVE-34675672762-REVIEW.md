## Actual failure and source evidence

The real native artifact shows the owned `Getting started` window at HWND
262498 in retained process 7724. The first `Select a theme` page advanced by
Enter after observing exactly `Select a theme. Next` as UIA focus and process
7724 as foreground. The second `Clip visualization` page was rendered correctly.
Its visible enabled `Next` button had bounds `[648,547,132,28]`, and the screenshot
shows that exact button in the lower right. UIA exposed no InvokePattern for it.

The helper then threw `No enabled accessible Next button or verified page focus`.
Its old implementation recorded focus only after the guard succeeded. The
artifact consequently does **not** establish which failed comparison was the
focused name, focused PID or foreground PID. No particular second-page focus
string is claimed as an observed fact.

The source explains why the surrogate's name cannot safely be inferred from the
page label alone. `FirstLaunchSetupDialog.qml` requests the active navigation
button, then calls the page's `readInfo()`. `Page.qml` exposes a separate
screen-reader surrogate named `%1. %2`, with its own page-sized rectangle.
`ClipVisualizationPage.qml` assigns the panel's accessible name from
`ClipVisualizationPageModel::navigationAccessibleName()`, which returns
`Clip visualization options`. Muse's `AccessibleItemInterface::text()` may
prepend `%1 panel, ` when `lastFocused()` and `needToVoicePanelInfo()` require it.
That supports the variable-prefix hypothesis but does not supply the missing
Windows focus observation.

The existing failure diagnostics also reported the main window outside the
1024x768 desktop. The owned onboarding image itself was complete (560x442).
Neither image is treated as marketing artwork or edited.

## Bounded correction

`GuiProbe.Advance()` now resolves exactly one enabled, visible, owned button with
the expected actual button name and role. It preserves InvokePattern when
available. Otherwise it clicks the center of that button's current UIA bounds
through native input, using no hard-coded screen coordinates or inferred focus
name. The separate page surrogate is never a click target.

Before moving the cursor and again immediately before sending mouse down/up,
the helper proves the retained process is alive, the exact native onboarding
HWND still owns the process, that exact HWND is foreground, and the native hit
window belongs to the same process and dialog root. The button, dialog, and
virtual-screen bounds must be valid, fully visible and unchanged. It reads back
the actual cursor position at the observed button center before input. Partial
SendInput completion fails qualification; a possible pressed mouse button is
released only if the same ownership, geometry and cursor checks still pass.

The scalar guard lives in `OnboardingInput.cs`, compiled into the same native
observer and directly exercised by the PowerShell tests. The receipt captures
both boundary observations, final cursor point and actual input count. The
independent Python verifier checks these against the captured UIA tree. The
previous exact keyboard-receipt policy remains unchanged for historical valid
receipts; the revised helper does not use a guessed keyboard fallback.

## Readable full-window evidence and restoration

The outer PowerShell watchdog now prepares the real native display before
starting the observer. The helper is adapted from CutQuay's reviewed
`script/marketing/display_modes.ps1` (Copyright 2026 Trieflow LLC, MIT). It
retains the exact primary display device and original DEVMODE, enumerates
supported modes, prefers an adequate 1920x1080 32-bpp mode, applies CDS_TEST
before a dynamic flags-0 change, and verifies the observed result. An already
adequate desktop is left unchanged. There are no registry, unsafe-mode, DPI,
renderer or emulation changes.

The restoration scope surrounds the observer's entire lifecycle, including its
180-second watchdog, owned process-tree stop, and diagnostics cleanup. Partial
native mode-apply failure also retains restoration responsibility. Restoration
compares the original mode's dimensions, position, bit depth, frequency,
orientation, flags and fixed-output mode. A restoration error fails the run and
is retained in `display-preparation.json`. Evidence is written exclusively and
includes the source commit. The independent GUI verifier requires adequate
native dimensions, permitted enumerated/tested mode selection and successful
restoration. The existing artifact metadata glob already retains this JSON;
no workflow YAML or binary artifact expansion was needed.
